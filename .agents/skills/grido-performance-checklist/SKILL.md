# قائمة فحص أداء Grido Studio

استخدم هذه القائمة عند مراجعة أو تعديل أي مكون في المشروع لضمان عدم إدخال مشاكل أداء أو تذبذب بصري في Konva أو Go backend.

---

## 1. فحص Canvas 2D / Konva Shape
- [ ] هل يتم استدعاء `fill()` أو `stroke()` داخل حلقة تكرارية؟ → يجب تجميعها في مسار واحد
- [ ] هل يتم استخدام `beginPath()` قبل كل `arc()` في حلقة؟ → يجب نقل `beginPath()` خارج الحلقة
  - *(نصيحة: استخدم `context.moveTo(x + r, y)` قبل كل `arc` لكسر المسار يدوياً ورسم آلاف النقاط بـ fill واحد).*
- [ ] هل يتم تغيير `globalAlpha` أو `fillStyle` داخل الحلقة بدون ضرورة؟ → يجب تثبيتها خارجاً

---

## 2. فحص استقرار Konva Stage و VRAM
- [ ] هل يتم تعديل أو خفض `pixelRatio` الخاص بـ Konva Stage ديناميكياً أثناء Zoom أو Pan؟ → يُمنع إجبارياً لتفادي إعادة تخصيص VRAM ومسح السياق وتذبذب البكسلات الفرعية.
- [ ] هل يتم استخدام `FastLayer` المهملة (Deprecated) في أي طبقة؟ → استبدالها دائماً بـ `<Layer listening={false}>`.
- [ ] هل `useEffect` الذي يستدعي `node.cache()` يراقب `dragX`, `dragY`, أو `zoom`؟ → يجب عزلها فوراً لمنع إعادة بناء قوام VRAM في كل فريم سحب.
- [ ] هل يتم تمرير `width` و `height` صراحة لعقد `<Group>` القابلة للتحجيم مع توفير fallback في `onTransformEnd`؟
- [ ] هل يتم استخدام `wrap="none"` و `ellipsis={true}` على نصوص Konva؟ → استبدالها بـ `wrap="word"` و `ellipsis={false}`.
- [ ] هل يتم تخزين ارتفاع النص المحسوب تلقائياً في `useState` محلي؟ → ممنوع، اقرأ `node.height()` وادفع القيمة المطبعة للـ Store مباشرة.

---

## 3. فحص React.memo و useMemo ومكونات الواجهة
- [ ] هل المكون يولّد عشرات عناصر SVG/DOM (مساطر، شبكات، قوائم)؟ → يجب تغليفه بـ `React.memo`.
- [ ] هل الحسابات الثقيلة (مصفوفات ticks، عناصر SVG) تتم داخل الرندر مباشرة؟ → يجب لفها بـ `useMemo`.
- [ ] هل يتم إنشاء كائنات جديدة (objects/arrays) في كل رندر داخل `.map()`؟ → يتسبب في كسر `React.memo`.
- [ ] هل يتم تصدير ثوابت أو مصفوفات من ملفات مكونات React (`.tsx`)؟ → يجب عزلها في `src/lib/...` أو `constants.ts` لحماية Fast Refresh ومعيار `--max-warnings 0`.

---

## 4. فحص إدارة الذاكرة (Memory)
- [ ] هل يتم استخدام `structuredClone()` على مصفوفات كبيرة؟ → استبدالها بـ `array.map(el => ({...el}))` في سجل التاريخ (سقف 30 لقطة).
- [ ] هل تحتوي الخوارزميات (مثل Flood Fill / Magic Eraser) على كائنات معقدة؟ → استخدم `Int32Array/Uint8Array` (Shared Buffers) لمنع إرهاق الـ Garbage Collector.
- [ ] هل يتم إنشاء `new Image()` داخل حلقة الطباعة/التصدير؟ → نقل الحساب إلى Go backend.
- [ ] هل يتم لف `setState` داخل `setTimeout(..., 0)` للتهرب من الـ Linter؟ → اشتقاق الحالة أثناء الرندر.

---

## 5. فحص توزيع المهام (JS ↔ Go & Wails v3)
- [ ] هل العملية تحتاج أبعاد الصورة الأصلية (naturalWidth/Height)؟ → Go أفضل (لديها الصورة مفكوكة).
- [ ] هل العملية تحتاج استجابة فورية للمستخدم (< 16ms)؟ → المتصفح أفضل.
- [ ] هل العملية تستهلك ذاكرة ضخمة (ZIP، طباعة 300DPI)؟ → Go أفضل (Stream to Disk).
- [ ] في حال تنفيذ مهام موازية في Go، هل يتم تقييد الخيوط (Goroutines)؟ → استخدم `errgroup` مع `g.SetLimit(runtime.NumCPU())`.
- [ ] هل يتم قراءة حالة الـ Store داخل الأحداث غير المتزامنة (مثل `handleDrop`) عبر Closure قديم؟ → استخدم دائماً `useEditorStore.getState()`.
- [ ] هل يتم استدعاء `f.Sync()` قبل `os.Rename` لكتابة الملفات الذرية لحمايتها من الانقطاع المفاجئ؟

---

## 6. فحص التكرارات غير الضرورية
- [ ] هل يتم إنشاء `TooltipProvider` في كل مكون فرعي؟ → يجب وجود واحد فقط في `App.tsx`.
- [ ] هل يتم استدعاء `pushHistory()` أثناء سحب السلايدر (60 مرة/ثانية)؟ → حصره عند `onDragEnd` أو غلق الـ Popover.
- [ ] هل يتم استدعاء `stage.toDataURL()` في أوضاع لا تحتاجه (كولاج)؟ → يجب تخطيه.

---

## 7. فحص التكبير والتحجيم (Zoom & Scaling)
- [ ] هل يتم تكبير الكانفاس (Zoom) عبر تغيير خصائص `width/height` في `Stage` وإعادة حساب إحداثيات كل عنصر في React؟ → يجب استخدام `transform: scale()` في CSS على الحاوية الخارجية (Wrapper) لتفادي إعادة تصيير Konva (Re-render) في كل حركة سحب لعجلة الفأرة، مع التقريب الأسي `Math.exp(-deltaY * factor)`.
