## 3. العلل المؤكدة — كلها أُصلحت

### 🔴 (كانت عالية) [A-01] استعادة الجلسة معطوبة: طرد إجباري عند كل تحديث صفحة

**الدليل (قياس لا قراءة):** العميل يُنشأ بـ`persistSession: false`، ثم يُستخدم `client.auth.getUser(savedToken)` — وهذه الدالة تستهلك التوكن لطلبها فقط **دون تحميل الجلسة على العميل** (مؤكد في `auth-js/dist/main/GoTrueClient.js:2622-2649`). القياس العملي للترويسات:

```
GET  /auth/v1/user          → Authorization: Bearer JWT_TOKEN_ABC     ← التوكن صحيح
POST /rest/v1/rpc/is_admin  → Authorization: Bearer ANONKEY...        ← يعمل كـ anon!
```

`is_admin()` تتحقق من `auth.jwt()->app_metadata->>'role'` أو عضوية `admin_users` — وكلاهما `null` لدور anon ⇒ النتيجة `false` ⇒ `clearSession()` ⇒ شاشة الدخول. وبما أن `_getAccessToken()` في `supabase-js/dist/index.mjs:807-812` تعود لمفتاح anon عند غياب الجلسة، فكل مسار الاستعادة كان فاشلاً بنيوياً، مع تخزين توكن ميت في `localStorage` (`grido_sb_token`) يوسّع سطح تسريب التوكن بلا فائدة.

**الأثر:** مشرف يعيد تحميل الصفحة (أو يعود بعد إغلاق التبويب) يُطرد دائماً، وكل «استعادة الجلسة والخدمات السحابية تلقائياً» المعلنة في نص الواجهة كانت غير موجودة.

**الإصلاح:** إدارة الجلسة تُركَت لـsupabase-js: `persistSession: true` + `autoRefreshToken: true` + `storageKey: 'grido_admin_auth'`، وإقلاع عبر `getSession()` ثم `rpc('is_admin')`، مع إزالة `grido_sb_token` وترحيل تنظيفي.

**التحقق بعد الإصلاح (قياس فعلي):** عميل أول يُسجّل الدخول ⇒ مفتاح واحد في التخزين (`grido_admin_auth`)؛ عميل ثانٍ (محاكاة إعادة تحميل) ⇒ `getSession()` تُعيد جلسة صحيحة ⇒ `rpc('is_admin')` يُرسل `Bearer <USER JWT>` (توكن الأدمن) لا مفتاح anon. ✅

**الإصلاح (الخيار الذي أوصى به التدقيق):** إعادة تسمية إلى «إعدادات محلية — مسودة المتصفح (LOCAL DRAFT CONFIG)»، شريط تحذيري صريح يشرح أنها لا تُدفع للخادم، رسالة حفظ صادقة، وتوحيد العنوان في الشريط العلوي والقائمة الجانبية.

### 🟠 [A-03] أرقام اللوحة مقصوصة بصمت (1000 صف API + 100 صف سجل)

**الدليل:** `select('*')` على `profiles` و`license_keys` بلا عدّ ⇒ PostgREST يقصّ عند `max_rows = 1000` (`supabase/config.toml:18`)، وسجل الذكاء مقصوص عند 100 صف، ثم تُعرض كلها كـ«إجمالي الحسابات» و«إجمالي عمليات الذكاء» و«GPU HOSTING COST».

**الأثر:** أي منصة تتجاوز 1000 حساب تُظهر أرقاماً ناقصة في المؤشرات والتوزيع وMRR بلا أي إشارة.

**الإصلاح:** عدّ خادمي دقيق لكل مؤشر (`count: 'exact', head: true` — لحسابات، مفاتيح، مفاتيح غير مستخدمة، عمليات الذكاء)، ووسم صريح للمعروض مقابل الكلي عند التقصير، وتسمية تكلفة الـ100 صف صراحةً (`AI COST (آخر N)` + «تكلفة آخر N عملية»).

### 🟡 [A-04] CSV Formula Injection في مصدري التصدير (بند سابق مفتوح)

**الدليل:** التصدير كان يستبدل الفواصل فقط؛ اسم مستخدم يبدأ بـ`=` أو `+` أو `-` أو `@` أو tab/CR يُنفَّذ كصيغة عند فتح الملف في Excel/Sheets (سلسلة `=cmd|...` معروفة)، واسم/بريد المستخدم بيانات يتحكم بها المستخدم نفسه.

**الإصلاح:** دالة `csvCell()` تُحيّد كل خلية تبدأ بمحارف الصيغ (`'` بادئة) وتهرّب الاقتباسات وتغلّف القيم، مطبَّقة على تصدير المستخدمين ودفعات المفاتيح، مع `URL.revokeObjectURL` لتنظيف الروابط المؤقتة.

**التحقق:** `csvCell('=cmd|calc')` ⇒ `"'=cmd|calc"`؛ و`csvCell('a,b')` ⇒ `"a,b"` (قيمة واحدة لا عمودان).

### 6.3 🔴 سلسلة تصعيد كاملة كانت حيّة على الإنتاج — أُغلقت الآن

**الحلقة ١ (رفع الصلاحية عبر الباقة):** `list_migrations` أعاد 16 هجرة تنتهي عند `20260801000001`، بينما المستودع فيه 18؛ الناقصتان `20260822000000` و`20260907000000`. والتعريف الحي لـ`is_admin()` كان يحتوي صراحةً:
`OR EXISTS (SELECT 1 FROM public.profiles WHERE id = auth.uid() AND plan = 'enterprise')`
⇒ أي مشترك Enterprise = مسؤول نظام كامل (SEC-01 حيّة). وكانت هناك **حسابتان** بباقة enterprise: حساب المالك المعتمد (`b2943199…`، صالح حتى 2036) وعميل حقيقي (`a60b8946…`، مشترك منذ 2026-08-31).

**الحلقة ٢ (رفع الصلاحية عبر RLS):** السياسات الحيّة على `profiles` كانت `UPDATE ... USING (auth.uid() = id)` **بلا `WITH CHECK`** (والافتراضي يساوي `USING`) ⇒ أي مستخدم يعدّل باقته/حالته/انتهاءه/مفتاحه بنفسه. الحلقتان معاً = مسار كامل من حساب مجاني إلى مسؤول نظام.

**السبب الجذري (مُثبت بتشغيل الهجرات فعلاً، لا استنتاج):** هجرتان في المستودع تستخدمان `OLD.plan` داخل `WITH CHECK`، وهو **غير صالح في سياسات RLS**:
```
ERROR: 42P01: missing FROM-clause entry for table "old"
```
فكانت `20260713000002` و`20260725000001` تفشلان كاملتين (transaction واحد) ولا تُثبَّت أي حماية، بينما تُسجَّلان في تاريخ الهجرات كأنهما نُفِّذتا. وهجرة ثالثة `20260907000000` تمنح `EXECUTE` لتوقيع **سباعي** لدالة لا يُنشئه أي ملف (التوقيع الوحيد هو السداسي بعمود `p_check_only`) ⇒ تفشل بـ`42883` ولا يمكن تطبيقها إطلاقاً. هذا يفسّر بدقة: بقاء سياسات `20260711000000` القديمة، وغياب `update_own_profile`/`admin_update_any_profile`، وغياب دالة `ensure_profile_exists` كاملةً (سقطت مع فشل `20260725000001`) — وهو نقص كان يعطّل مسار الإنشاء الاحتياطي في تطبيق سطح المكتب.

**ملاحظة تشغيلية كانت حاسمة:** `admin_users` كان فارغاً (0 صف)، ولأن تعريف `is_admin` المُصلح لا يعتمد إلا على عضوية `admin_users` أو `app_metadata.role='admin'` (وكل الـJWT في المشروع بلا هذا الدور)، فإن أي تطبيق أعمى كان سيُخرج المشرف من اللوحة فوراً. لذلك نُفِّذ الإدراج **قبل** إصلاح الدالة.
